# Офлайн-режим и синхронизация

На управляемом планшете работает лёгкое POS-приложение с подписанным локальным пакетом SKU/цен/разрешённых промо, ограниченным списком прав кассира и зашифрованным durable journal (например, embedded SQLite, без отдельного сервера БД). Локальный HAL через сертифицированный драйвер управляет фискальным регистратором и банковским терминалом; браузер напрямую USB не использует. Без интернета разрешены наличные продажи из ещё действующего каталога и офлайн-допустимых категорий. Чек фискализируется на местном устройстве, данные для ОФД передаются по его штатному протоколу после восстановления связи. Списание бонусов и сетевые резервы Click & Collect отключены, начисление может быть pending. Оплата картой допустима только если конкретный терминал и эквайер подтверждают её по собственному каналу; POS не объявляет платёж успешным по локальному предположению. Срок автономности предлагается 24 часа, но зависит от срока каталога, прав кассира, ФН, требований к товарной категории и доступной ёмкости; после нарушения обязательного условия соответствующая операция блокируется.

До фискальной команды POS устойчиво записывает `sale_id=(store_id,device_id,local_sequence)`, строки, суммы, версии цен/налогов и статус операции. После ответа HAL сохраняет идентификатор фискального документа/ФН и результат оплаты; печать выполняется по утверждённому протоколу ККТ. Crash после фискализации до ACK обрабатывается запросом статуса/чтением фискального документа, а не повторной выдачей чека. Если драйвер не позволяет однозначную проверку, операция переводится на ручную сверку и новая фискализация автоматически не выполняется. При возвращении сети Sync Agent отправляет последовательные пакеты outbox с идемпотентным sale ID; Cloud Backend транзакционно сохраняет inbox и продажу, затем подтверждает непрерывный checkpoint. Повтор того же ID и payload — no-op, другой payload — карантин. Локальная запись очищается только после durable ACK облака и установленного срока хранения; облачный ACK не означает, что SAP уже завершил учёт.

В облаке отдельный outbox доставляет подтверждённую продажу в SAP и Smart Fulfillment. Адаптер SAP использует тот же внешний ID и проверку статуса при неизвестном результате; если API не поддерживает идемпотентность, нужен реестр обработанных ID в импортном контуре SAP. Остатки изменяются документами продаж/возвратов, а не last-write-wins заменой снимка. Изменившаяся после продажи цена не переписывает уже выданный чек; расхождения направляются на сверку. Новые каталоги загружаются отдельно, проверяются по подписи/manifest и атомарно активируются между продажами; начатая корзина фиксирует версию. Устаревший магазин исключается из обещания доступного C&C-остатка или получает safety stock; после догона очереди сверяются gap-free sequence, число чеков и суммы с ФН/эквайрингом/SAP, и только затем снимается режим деградации. Потеря планшета до синхронизации оставляет риск потери невыгруженного журнала: ФН помогает восстановить фискальные факты, но не все служебные данные, поэтому RPO 0 для офлайн-периода не обещается.
