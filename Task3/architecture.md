# Целевая архитектура VitaStore

## Границы решения

Cloud POS предоставляет центральный backend и лёгкое управляемое приложение на планшете. Это offline-capable thin client: минимальные правила наличной продажи, каталог и журнал остаются локально. Требование полностью убрать любые локальные данные несовместимо с продажей без интернета, поэтому ликвидируется отдельный сервер магазина, а не durable storage планшета. Фискальный регистратор, сканер/принтер при необходимости и банковский терминал остаются периферией; фраза «только планшет и регистратор» не означает исчезновения эквайрингового устройства.

В облаке находятся POS backend, публикация версий каталога, intake продаж, интеграционный адаптер SAP, очередь, PostgreSQL и object storage. Сервисы onboarding/SKU используют тот же управляемый стек, но отдельные права/таблицы/очереди; они не блокируют обслуживание касс. Promo Engine публикует ограниченные подписанные правила, которые умеет локальный POS. Smart Fulfillment остаётся собственным продуктом и мигрирует на PaaS; SAP остаётся on-premises, соединён с облаком через защищённый интеграционный канал. [C4 HLD](diagrams/to-be.puml) показывает контейнеры, а не обещание единственного процесса для всего backend.

## HAL и Payment Gateway

HAL — локальный управляемый агент/SDK на поддерживаемой ОС планшета, независимо обновляемый от UI кассы. Порт кассы: `startPayment(operation_id, amount, currency)`, `getPaymentStatus(operation_id)`, `refund(original_payment_id, operation_id)`, `fiscalize(sale_id, receipt)`, `getFiscalStatus(sale_id)`, `deviceHealth()`. Ответы содержат состояние и ссылки, но не PAN/PIN. Команды ограничены доверенным приложением через OS IPC/защищённый loopback с аутентификацией; произвольный сайт не может вызвать фискализацию.

Адаптер связывает порт с сертифицированным протоколом конкретного производителя, эквайера, firmware и ОС. Он не превращает Windows-only DLL в Android SDK. Если ARCUS-2 или фискальное устройство не поддержано выбранным планшетом, применяются подтверждённый вендором SDK/совместимое устройство либо замена; временный внешний bridge — исключение с отдельным TCO и датой удаления. На HLD целевой HAL находится на планшете, новый сервер в подсобке не появляется.

Cloud Payment Gateway нормализует идентичность мерчанта, маршруты, конфигурации и онлайн-сверку. Физический банковский терминал обменивается платёжными данными с эквайером по сертифицированному каналу; облако не туннелирует произвольные USB-команды. Timeout оплаты — неизвестный исход: проверка того же operation ID, без повторного списания; фискальная компенсация/возврат — отдельные документы. Утверждение «любой терминал подключится автоматически» заменено управляемым каталогом совместимости и независимыми адаптерами.

## Данные и надёжность

| Данные | Источник истины | Реплика/доставка и правило |
|---|---|---|
| SKU, цены, налоги | SAP и утверждённые коммерческие правила | Версионированный пакет в cloud storage и на планшетах; меняется атомарно |
| Продажа и фискальный факт | ФН/чек + локальный sale journal до ACK; durable cloud receipt после ACK | Идемпотентный outbox/inbox, сверка по sale ID и fiscal document ID |
| Бухгалтерский учёт | SAP | Проверенный импорт по внешнему ID; нет прямой записи POS в SAP DB |
| Платёж картой | Эквайер | Ссылки на транзакцию и журнал статусов; timeout не равен отказу |
| Бонусный баланс | Централизованный loyalty ledger | Offline accrual pending, offline redemption запрещён в первом релизе |
| Остатки/заказы C&C | SAP для учёта, Smart Fulfillment для обещаний/резервов | Версии и события; stale-store flag, safety stock, запрет нового локального обещания без связи |
| Mapping SKU | Версионированная таблица решений Data Integration | Master_version, reviewer, модель/правила и evidence; только подтверждённые mappings импортируются |

Облачный PostgreSQL — managed HA по зонам с подтверждением устойчивого commit, backup/PITR и тестами восстановления. Рабочие цели: RPO 0 подтверждённых cloud receipts при единичном отказе узла/AZ при соответствующей конфигурации, RTO ≤30 мин; региональный disaster RPO ≤15 мин только при доказанном режиме копирования и RTO ≤4 ч — предложения для согласования. Если async lag не ограничен, фактический RPO равен хвосту репликации, а не обещанным 15 минутам. Кассы продолжают разрешённые offline-операции в пределах срока каталога. Потеря планшета может потерять несинхронизированные данные; ежедневный облачный backup этого не исправляет. Для восстановления нужны ФН, сменный планшет и runbook сверки.

TLS/mTLS, device certificates, MDM, encrypted storage, least privilege и журнал действий защищают доступ. Offline cashier access использует короткие подписанные разрешения, поэтому отзыв пользователя без сети не мгновенный. PAN/PIN остаются в сертифицированном платёжном контуре. Требования 54-ФЗ, маркировки, персональных данных и эквайринга подтверждаются профильными специалистами на конкретном ассортименте; «наличные всегда доступны для любого товара» нельзя гарантировать вне этих условий.

## Переход и эксплуатация

| Период | Содержание и выходной критерий |
|---|---|
| Недели 1–2 | Discovery: фактический поток SAP, лицензии, оборудование/прошивки, тарифы и договоры; baseline календаря/ошибок/TCO |
| Недели 3–4 | RFP/тест SaaS и HAL; pipeline SKU; golden set; проверенный API/import SAP и receipt identity |
| Недели 5–8 | Пилот 5–10 точек, controlled offline, crash/replay, restore, проверка пятидневного онбординга; решение о масштабировании |
| Месяцы 3–12 | Волны миграции по совместимости устройств, обучение, снижение legacy-объёма; перенос собственных HQ-продуктов отдельными волнами |

На точке сначала импорт и shadow-сверка без двойной фискализации; затем одна касса/canary, потом весь магазин. Каждая реальная продажа имеет единственного владельца. Перед выводом сервера сверяются документы, архив и договора лицензий; восстановление старого POS возможно только после остановки нового пути и переноса подтверждённых продаж. ФН и платежи не откатываются восстановлением SQL-backup. Помесячная модель TCO считает отдельную волну 100 магазинов после пилота: шесть месяцев rollout, включая один месяц двойной эксплуатации каждой точки; годовой план всей сети и этот финансовый периметр различаются.

Store Ops владеет fleet/HAL/кассовыми инцидентами; Data Integration — matching/ERP/replay; HQ-коммерческий — master и спорные товары; продукт логистики — Smart Fulfillment; IT-дирекция — облачные расходы, доступы и DR. Нужны метрики возраста каталога, количества pending receipts, oldest outbox age, sequence gaps, доли несовместимого оборудования, отказов фискализации, ошибок сопоставления, SaaS/PaaS cost/store и человеко-часов подключения.

## Проверка решения

1. Отключить интернет на контрольный период: наличная продажа допустимого товара, фискальный чек, сохранение журнала; ни списания бонусов, ни ложного успеха оплаты картой.
2. Убить POS после фискализации до записи ответа: восстановление статуса без второго чека; при недоказуемом результате — сверка.
3. Повторить/переставить upload batch, потерять ACK облака и SAP: одна продажа/одна бухгалтерская запись, gaps видны.
4. Сменить каталог во время корзины: сумма/налог соответствуют зафиксированной версии; некорректный пакет не активируется.
5. Подключить реальную матрицу банковских/фискальных устройств: установка адаптера без пересборки POS; неподдерживаемый вариант не проходит gate.
6. Восстановить managed DB и новый планшет, сверить ФН/эквайринг/SAP; замерить RPO/RTO и стоимость.

Это проектные критерии, а не выполненные тесты VitaStore. Механизм синхронизации кратко изложен в [трёх абзацах](offline-sync.md).
